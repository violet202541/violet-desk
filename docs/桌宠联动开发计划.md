# Violet 桌宠联动开发计划

版本：v1.0｜编制日期：2026-10-10｜状态：开发方案，尚未实施

> 产品目标：做一个好看、可爱、动作自然，并能与 Violet 音乐、任务、日历、日记联动的桌面陪伴角色。提供可选的紧凑键盘和真实按键映射。以角色表现和日常使用体验为优先，技术方案围绕这两个目标展开。

## 1. 已确定的需求与交付边界

### 1.1 正式版必须包含

- 一个精修的 2D 桌宠，支持待机、听歌、打字、递信、庆祝和休息。
- 透明悬浮窗口、拖动、多屏定位、大小调整、置顶开关、鼠标穿透、隐藏与恢复。
- 与现有音乐播放、任务完成、专注计时、日历提醒、日记保存和封存联动。
- 可选显示紧凑键盘；可独立开关真实键盘联动与按键音效。
- 字母、数字行、常用修饰键、空格、回车、退格、方向键和 Delete 的映射。
- 可修改的全局快捷键，用于显隐、切换模式和音乐控制，并提示快捷键冲突。
- 白天／夜间适配，免打扰，提醒去重，后台节能，异常恢复。
- 跟随真实音乐强弱的轻微律动模式；与普通听歌动作分开控制。
- 打包后可从现有 Violet 启动和管理，关闭桌宠后原有功能正常使用。

### 1.2 首发取舍

- 第一平台为 Windows 10／11 x64；跨平台输入监听留接口，首发只承诺 Windows 验证结果。
- 一个主角色、一套紧凑键盘、一套统一道具，先把这套资源做精。
- 保留当前主程序的 Vue + pywebview；新增独立 Tauri 桌宠进程。
- 全局输入只用于即时动作映射；不拦截、不替换用户实际输入，不记录输入文本。
- AI 聊天、语音对话、复杂养成、多角色、自由走动与攀爬窗口属于后续扩展，不作为此次桌宠联动的前置依赖。
- 本次交付是开发计划，不自动启动代码迁移、素材采购或模型制作。

## 2. 当前项目基础与实际缺口

以下依据当前工作区源码核对，不能把“已有接口”视为“桌宠联动已完成”。

| 现有能力 | 已有位置 | 可以复用 | 本次要补 |
|---|---|---|---|
| 桌面入口、托盘和窗口管理 | violet_app.py | 启动、单实例、隐藏到托盘 | 桌宠进程管理、显隐入口、退出协调 |
| 本地 HTTP、令牌和 SSE | violet_server.py、web/src/api.js | 业务命令与推送通道 | 桌宠专用状态快照、事件、连接恢复、协议版本 |
| 音乐播放 | web/src/player.js | Audio、队列、播放模式、音量 | 播放状态镜像、显式控制命令、执行回执 |
| 任务、日历、日记 | violet_desk.py、web/src/desk.js | desk.db、revision 冲突检测、现有业务接口 | 成功提交后的统一事件和主界面刷新 |
| 专注计时 | web/src/components/FocusOverlay.vue | 现有操作流程、完成记录 | 将进行中的会话状态抽离为服务端权威状态 |
| 到期提醒 | VioletService.check_reminders | 到期判断、reminder 事件 | 单一投递决策、稍后提醒、去重和恢复 |
| 页面导航 | web/src/store.js 的 go 与 navigate | 切换大页面 | 携带记录 ID／日期并打开对应记录 |
| 下载与来信 | job、drained 事件及 letters 接口 | 完成状态、来信数据 | 批量合并反馈、当天来信入口 |
| 发布打包 | tools/build_exe.py | 现有 PyInstaller 流程 | 一起分发桌宠可执行文件、资源和版本信息 |

关键判断：
1. 当前音乐在主窗口的网页 Audio 中播放。桌宠不能只查询 SQLite 来判断播放状态，也不能再创建一个播放器播放同一首歌。
2. 专注倒计时目前在 Vue 组件内计算。仅转发“开始”事件无法保证重连、暂停、延长后的双端一致性。
3. 当前提醒已发送 SSE，并调用系统通知钩子。桌宠必须参与投递决策，避免应用提示、桌宠和系统通知同时重复响铃。
4. 任务／日记写入接口已有基础，但许多成功操作没有对应跨窗口业务事件，需要在提交成功之后补齐。

## 3. 技术架构

### 3.1 技术选型

| 层 | 选型 | 职责 |
|---|---|---|
| 桌宠外壳 | Tauri 2 + Rust | 窗口、生命周期、原生输入、快捷键、与本地服务连接 |
| 角色渲染 | Live2D Cubism SDK for Web | 模型、表情、呼吸、物理、动作混合 |
| 原画与动画制作 | 分层 PSD + Cubism Editor | 精修原画、拆层补绘、绑定、动作工程 |
| 桌宠 UI | Vue 3 + TypeScript | 气泡、设置、菜单、键盘布局与状态 |
| 道具渲染 | 与角色协调的 Canvas／WebGL 绘制层 | 键帽、纸张、轻量粒子与道具动画 |
| 业务后端 | 现有 Python 服务 | 业务数据、提醒、专注会话、桌宠状态镜像 |
| 持久化 | 现有 SQLite + 独立桌宠配置 | 业务仍由服务管理；桌宠不直接写业务数据库 |
| 业务通信 | HTTP 命令 + SSE 事件 | 复用现有机制；初版不为桌宠整体引入新服务框架 |
| 键盘输入 | Windows Raw Input | 后台按下／松开事件，转为动作参数 |
| 控制快捷键 | Tauri global-shortcut 插件 | 可配置组合键与注册冲突处理 |

第一版直接验证官方 Cubism Web SDK；封装成 PetRenderer 接口。不要先将第三方 Live2D 包与其他渲染库随意组合，再承担版本兼容问题。

### 3.2 运行关系

```text
现有 Violet 主窗口（Vue + pywebview）
       │ 音乐状态、页面状态、显式控制命令与回执
       ▼
现有 Python 服务 ── SQLite：任务／日历／日记／专注
       │
       │ HTTP + SSE：快照／事件／命令
       ▼
桌宠 Tauri 进程
  Rust：连接管理、窗口、原生输入
       │
       ├─ 原生按键 → 内存映射／状态合并 → 动画层
       └─ 业务事件 → 行为调度 → Live2D + 道具 + Vue 气泡
```

按键路径不经过 Python 服务和数据库。服务只接收业务操作及低频状态。桌宠默认通过 Rust 连接本机服务，再将规范化事件交给前端，避免开放宽泛跨域访问。

### 3.3 生命周期

- Violet 设置内开启桌宠，由主程序启动一次；重复点击只唤起现有桌宠。
- 主窗口隐藏到托盘时，播放器、服务和桌宠继续工作。
- 明确“隐藏桌宠”“关闭桌宠”“退出 Violet”三个动作：隐藏可通过快捷键恢复，关闭仅停桌宠，退出 Violet 会结束相关进程。
- 单独启动桌宠时先发现已有 Violet 服务；找不到则引导启动 Violet，并显示离线待机状态。
- 服务断开后桌宠撤下过期业务信息，保留本地待机和键盘模式；重连后先同步快照。
- 令牌通过受控本地通道交接，不写进调试日志；继续只连接 127.0.0.1。
- 打包模型、道具和字体到本地，核心陪伴不依赖联网。

## 4. 视觉方向：可爱，但要有完成度

### 4.1 角色方案

以现有 Grok-bot 头像为视觉起点：奶油色脸、胶囊眼、蜂蜜金发、暗红丝带、祖母绿胸针，扩展为完整 Q 版角色。

- 约 2.5～3 头身，脸和双手优先清楚；身体比例以定稿图为准。
- 日常姿态采用略俯视的正面坐姿，能看清脸、双手和键盘。
- 保留无嘴或极简面部路线，通过眼睛压缩、歪头、肩膀和手势表达情绪。
- 不使用过强高光、复杂描边和密集纹理；小尺寸也应看得清角色轮廓。
- 日间使用奶油白、旧纸与低饱和紫；夜间降低道具亮度，保留角色辨识度。
- 呼吸、头发和丝带运动要克制；没有事件时保持安静，不持续大幅摇摆。

现有头像用于托盘、迷你模式、加载与模型故障回退。先前的右下探入版本可以作为递信姿态参考，正式全身模型不能直接由头像替代。

### 4.2 尺寸与构图初值

- 角色常规显示高度约 240～320 逻辑像素；默认从 280 开始做桌面实测。
- 带键盘时整体宽度约 320～380 逻辑像素，键盘宽度约为肩宽的 1.2～1.4 倍。
- 提供约 70%～150% 的整体缩放，角色与键盘保持比例。
- 迷你模式约 80～120 逻辑像素，只显示头像或半身；关闭键帽细节以保证清晰。
- 气泡出现在不遮脸的一侧，靠近屏幕边缘时自动换边；菜单和气泡尺寸单独保证可读性。

这些数值是设计起点。最终以用户电脑、显示缩放和实际壁纸下的效果为准。

### 4.3 视觉验收

- 深色、浅色、复杂壁纸下均无白边、黑边或透明底杂色。
- 默认尺寸能分清左右手、眼睛和主要道具；缩小后脸部不糊成一团。
- 转头、抬手和换道具时无缺口、穿模、错误遮挡或边缘拉裂。
- 动作之间有自然过渡，手、道具与目光方向一致。
- 连续观看 10 分钟不会频繁看到明显跳帧、突然归零、夸张重复动作。
- 夜间不出现大面积强白光；键盘灯效只做低亮度局部反馈。

## 5. 美术资源生产计划

### 5.1 制作顺序

1. 生图探索 2～3 个造型方向，保持同一角色特征，选定一个进入精修。
2. 产出全身定稿、配色表、脸部表情规则、键盘坐姿与四个动作关键图。
3. 按动作需求制作分层 PSD，补绘被头发、衣服和手遮挡的区域。
4. 在 Cubism 中制作网格、变形器、基础参数、物理和表情。
5. 制作动作、过渡和道具同步标记，接入真实桌面窗口验证。
6. 根据默认尺寸、键盘响应和背景适配结果返修。

生图用于概念、道具设计和关键姿态参考；正式交付必须包含可编辑的拆层与绑定工程。逐帧独立生图容易造成角色细节漂移，不作为主要动画制作方法。

### 5.2 必交素材

| 类别 | 交付内容 | 验收重点 |
|---|---|---|
| 角色设定 | 定稿全身、配色、细节、桌面尺寸预览 | 风格一致，缩小清晰 |
| 分层原画 | PSD；脸、眼、前后发、丝带、躯干、衣袖、左右臂手分层 | 拆层够用，遮挡区域已补绘 |
| 模型 | 可编辑工程、model3.json、moc3、纹理图集 | 能重新导出，可在目标 SDK 加载 |
| 动作与参数 | motion3、exp3、physics3、参数和动作清单 | 命名稳定，循环和过渡可验证 |
| 紧凑键盘 | 外壳、键帽状态、布局 JSON、各键位置与命中区域 | 与角色透视一致，字形清楚 |
| 道具 | 耳机、信封、信箱、印章、小打字机、纸张 | 比例、光源、线条风格统一 |
| 音效 | 少量轻敲、纸张、回车、盖章声音 | 默认克制，独立音量，不叠加炸响 |
| 回退资源 | 透明 PNG 头像或半身 | 模型故障时仍可显隐、打开设置 |

键盘标识使用程序排版或人工校正，不依赖生图生成可读字母。确认素材来源和发布所需授权；模型由外部制作时，将可编辑工程与运行文件一起列入交付。

### 5.3 动作清单

| 状态 | 必要表现 | 可叠加因素 |
|---|---|---|
| 待机 | 呼吸、眨眼、轻微歪头、偶尔整理发梢 | 短暂目光跟随 |
| 听歌 | 戴耳机／听歌姿态、轻点头 | 可选音乐强弱律动 |
| 键盘 | 左右手独立抬起、下压、松开 | 真实按键、同侧连续按键 |
| 专注 | 安静打字／工作姿态 | 专注时间、键盘模式 |
| 递信 | 探身、取出信封、递出 | 日程／任务／来信气泡 |
| 完成 | 盖章、轻点头或短暂开心表情 | 单次完成、批量完成合并 |
| 日记封存 | 整理纸张、装入信封或信箱 | 保存与封存使用不同强度 |
| 休息 | 放下手、打盹、恢复 | 闲置、免打扰、夜间 |

键盘模式使用紧凑键盘；专注模式可切换打字机道具。两套道具共享角色和手部参数，视觉键位只在紧凑键盘模式中准确映射。

## 6. 可选键盘映射

### 6.1 布局

采用接近 65% 的紧凑布局，实际键数在美术定稿时确定：

- QWERTY 字母区、数字行和常用标点。
- Esc、Tab、Caps Lock、左右 Shift、Ctrl、Alt、空格、Enter、Backspace。
- 方向键和 Delete；不显示独立数字小键盘或单独的 F1～F12 行。
- Windows 键等系统键可映射为对应修饰键反馈，不改变系统原有行为。
- 画面没展示的键仍允许配置为动作触发，不强行给键盘增加区域。
- 初版按物理键位映射；键帽显示与输入法输出分离，中文输入法下不尝试重现输入文字。

### 6.2 独立选项与默认值

| 选项 | 默认 | 行为 |
|---|---|---|
| 显示键盘 | 开启 | 显示桌宠面前的紧凑键盘 |
| 键盘联动 | 关闭，首次明确开启 | 开启后监听真实按键并驱动双手 |
| 按键音效 | 关闭 | 独立音量，避免与音乐和专注提示叠加 |
| 键帽下压／低亮高亮 | 开启 | 跟随按下与松开状态 |
| 快速输入增强动作 | 开启，可关闭 | 轻微加强动作，限制最大幅度 |
| 空闲时收起键盘 | 关闭，可开启 | 过渡后隐藏，恢复输入时重新展开 |

隐藏键盘时若联动仍开启，角色可做简化双手动作，不展示不存在的键帽；设置文案明确两项区别。关闭联动后释放原生输入订阅并清空按键状态。

### 6.3 输入与动画规则

- 按键按下、保持、松开分别处理，重复 KeyDown 不累积无穷动画队列。
- 多键同时按下时保留每个键帽状态；双手动画按左右区域合并。
- 同侧快速输入时在当前动作基础上调整目标，不反复重播完整动画。
- 空格触发拇指／双手中部动作；Enter 触发较明显反馈；回车拨杆仅用于打字机道具。
- 手部即时反馈优先于头部装饰动作；递信等完整手部动作期间不让键盘强行抢占，最多保留键帽反馈。
- 拖动、休眠恢复、输入设备重连、停止监听时清空卡住的按键状态。
- 不抑制普通系统按键；Raw Input 用于观察事件。控制快捷键另行注册、检查冲突。
- 默认只在内存保留当前按键集合与短时动作强度，不持久化扫描码序列或文本。
- 设置中提供一键暂停键盘联动，不需要退出桌宠。

## 7. 与现有功能的联动矩阵

| 功能 | 触发时机 | 桌宠反馈 | 可执行操作 | 开发接点 |
|---|---|---|---|---|
| 音乐 | 播放／暂停／切歌 | 耳机、动作变化、小唱片信息卡 | 播放、暂停、上一首、下一首、音量 | player.js 状态桥 + 显式命令 |
| 音乐律动 | 用户开启律动且正在播放 | 小幅随音乐强弱摆动 | 开关律动、调节强度 | Web Audio 分析 + 限频状态 |
| 下载 | 一批结束或出现失败 | 收信／简短结果提示 | 打开下载结果、查看失败项 | job／drained，批量合并 |
| 每日来信 | 当天有可读来信 | 拿着信封等待 | 打开当天来信 | letters 接口与导航 |
| 任务 | 创建／完成／当天全部完成 | 记下、盖章、轻庆祝 | 打开任务、明确标记完成 | 业务提交后的事件 |
| 专注 | 开始／暂停／恢复／结束 | 打字机、安静工作、休息 | 打开计时、暂停／恢复、结束 | 服务端专注会话 |
| 日历 | 到期日程／纪念日 | 递信与简短卡片 | 打开记录、稍后提醒 | reminder、持久化 snooze |
| 日记 | 打开编辑、保存成功、封存成功 | 陪写、整理信纸、投递 | 打开今天日记／对应记录 | 编辑态桥 + 成功提交事件 |
| 每周封存 | 封存成功 | 收起一叠信，盖章 | 打开周回顾 | weekly 成功事件 |
| 主题与闲置 | 主题变化、长期闲置 | 光照／气泡适配、休息 | 切换模式、隐藏 | 主题状态、单调时钟 |

保存失败不播放“已保存／已完成”的庆祝。日记只使用记录 ID 和编辑／保存状态，不把正文传给桌宠。收藏和歌单后续可增加轻反馈，不阻塞上述功能交付。

## 8. 状态同步与事件协议

### 8.1 业务数据与事件

建议新增协议模块，明确 protocol_version、event_id、session_id、sequence、type、occurred_at、entity_id 与 payload。

建议事件命名（均为拟新增，不能当作现成接口）：
- music.state、music.command_result
- focus.state、focus.finished
- commission.completed、appointment.reminder
- reply.saved、reply.sealed、weekly.sealed
- download.batch_finished、theme.changed

原则：
- 持久化成功后再发业务事件。
- 快照用于还原当前状态；事件用于触发一次性动作。
- 使用事件 ID／实体 revision 去重；重连后恢复快照，不重演所有历史庆祝。
- 重要提醒采用持久化投递记录和确认，不依赖无历史的 SSE 广播保证送达。
- 普通动作队列有上限，同类事件合并；过期动画不补播。

### 8.2 音乐控制

- 主播放器是唯一播放执行者；对桌宠同步曲目、播放状态、音量、位置时间戳和可用性。
- 使用 play、pause、next、previous、set_volume 等明确指令，避免重试 toggle 导致反向操作。
- 命令包含 command_id，播放器返回成功／失败回执；超时不假装执行成功。
- 状态变化立即同步，进度低频校准；桌宠本地推算展示，不逐帧走 HTTP。
- 主窗口隐藏时继续播放；播放器实例销毁时明确显示不可用，并提供打开主窗口入口。
- 音乐分析使用独立可关闭分支：测量低频能量／整体强弱、平滑与限幅，约 10～20 Hz 上报。
- 首版不声称精准节拍识别；若要精确跟拍，再评估节拍检测与曲目预分析。
- 试听验证分析节点不会产生双声、静音、异常增益或明显音画不同步。

### 8.3 专注会话

- 新增会话 ID、关联任务、目标时长、累计时长、暂停状态、版本与完成标记。
- 由服务端管理状态转移，主窗口与桌宠作为显示和操作端。
- 倒计时不依赖界面 setInterval 累加；使用权威时间和本地平滑显示。
- 暂停／恢复／延长／结束均以命令提交并回传状态。
- 明确休眠期间默认暂停专注，恢复时重建时间基准；不将系统休眠直接记为工作时间。
- 原有 focus 完成记录保留，按会话 ID 保证只入库一次。

### 8.4 记录导航与数据一致性

- 扩展 navigate 为白名单目标：页面、记录 ID、日期、操作模式。
- 桌宠点击“打开”时先唤起主窗口，再打开相应任务抽屉、日历日期或日记。
- 同一记录不存在或已删除时，回退到对应列表并显示明确提示。
- 主窗口接收桌宠引发的数据变化后刷新相关数据，不要求用户手动切页。
- 桌宠修改记录继续使用现有 revision 冲突保护，不绕过服务直接写数据库。

## 9. 行为调度与提醒体验

行为拆成“基础状态 + 身体动作 + 表情 + 手部输入 + 气泡”，避免简单字符串状态把全部效果互相覆盖。

优先级建议：
1. 用户正在拖动／点击／操作菜单。
2. 需要处理的到期提醒和用户主动触发的完整动作。
3. 当前键盘与专注操作。
4. 音乐陪伴。
5. 待机与随机装饰动作。

实际以动作占用部位判断可否叠加，例如键盘双手与轻微头部点动可以共存。

提醒规则：
- 一个提醒只有一个主要有声投递渠道。
- 桌宠可见且已确认接收时优先桌宠展示；桌宠关闭、不可达或未确认时回退系统通知。
- 全局免打扰开启时保持静默记录，除非用户单独允许某类提醒；不借系统通知绕过免打扰。
- 用户可设置全屏应用时自动隐藏、安静时段、气泡显示时长。
- 普通庆祝和随机动作设置冷却；连续完成任务合并为一次反馈。
- “稍后提醒”保存新的到期时间，跨重启有效；多个窗口同时操作只执行一次。
- 点击桌宠打开菜单应立即响应，不必等待正在播放的动画结束。
- 恢复鼠标穿透必须有稳定入口：托盘与可配置快捷键至少保留一种。

## 10. 桌面能力与性能标准

### 10.1 窗口与输入

- 透明内容与矩形窗口边界分开处理；透明背景不能误挡住其他应用。
- 交互模式中角色和可见控件可点击，空白区域应穿透。整窗穿透时所有桌宠内容都不接收点击。
- Tauri 的整窗忽略鼠标接口不能自动提供像素级命中，需要在技术验证阶段做 Alpha／命中区域与 Windows 命中测试方案。
- 桌宠默认不抢焦点；文本设置界面需要输入时单独激活。
- 保存显示器标识和逻辑坐标，处理负坐标、多屏 DPI、任务栏工作区、热插拔。
- 显示器断开后将角色移到可见工作区；不留在无法找回的屏幕外。
- 休眠、锁屏、恢复后重建窗口／输入状态；不宣称能够在安全桌面接收输入。

### 10.2 性能验收目标

以下是待实测目标，不是现有性能结论。P0 记录实际测试设备、分辨率与电源模式后锁定门槛。

| 指标 | 初始目标 |
|---|---|
| 活跃动作 | 默认 60 FPS，帧间隔 p95 不高于约 20 ms |
| 安静待机 | 约 30 FPS，可进一步降频 |
| 隐藏／锁屏 | 停止非必要绘制，不持续运行 60 FPS |
| 按键到可见动作 | p95 小于 80 ms，记录采样方法 |
| 新增桌宠进程 CPU | 测试机待机平均不高于约 3%，活跃平均不高于约 8% |
| 新增桌宠进程内存 | 暂以稳定后不高于 300 MB 为目标，按实测调整图集与资源策略 |
| 长时运行 | 8 小时无崩溃、卡键、明显持续内存增长 |
| 服务中断恢复 | 有明确离线状态，重连后状态一致、不重播历史庆祝 |

WebView／GPU 进程一起计入桌宠成本。交互和动画验证要覆盖正在播放音乐与连续输入的场景，不能只测静止空窗口。

## 11. 开发阶段与里程碑

工期为规划估算：按 1 名熟悉技术的工程师，另有原画／绑定制作支持，预计工程约 29～44 个工作日；美术与绑定约 15～30 个工作日可部分重叠。整体可按约 6～10 周排期，实际以 P0 与角色定稿结果重估，不包含外部作者排队时间。

| 阶段 | 估算 | 工作与交付 | 进入下一阶段的标准 |
|---|---|---|---|
| P0 技术验证 | 3～4 天 | Tauri 透明窗、现成合法测试模型、后台输入、多屏、穿透、连接现有服务 | 无焦点也能响应键盘；空白不挡操作；透明边缘正常；性能基线记录 |
| P1 视觉定稿与资产规范 | 工程协同 2～3 天；美术另排 | 定稿图、键盘布局、四个关键姿态、拆层规范、参数协议 | 默认桌面尺寸可读，手与道具透视正确，原画可支持动作 |
| P2 桌宠基础 | 4～6 天 | 模型加载、待机、窗口设置、进程管理、主题、离线和回退 | 模型可替换；显隐缩放定位可保存；独立失败不影响主应用 |
| P3 键盘与动画 | 5～7 天 | 紧凑键盘、独立手部参数、多键输入、开关、快捷键、音效 | 连续输入、多键、长按、休眠后无卡键；关闭联动立即生效 |
| P4 业务联动 | 7～10 天 | 音乐控制、专注会话、任务、日历、日记、来信、导航、提醒去重 | 所有矩阵场景闭环；失败无假反馈；双端数据同步 |
| P5 表现精修 | 4～7 天 | 动作混合、音乐律动、粒子与道具、夜间、免打扰 | 动作自然、不抢输入、不重复提醒，真实音乐分析不影响播放 |
| P6 验证与发布 | 4～7 天 | 多屏 DPI、长时运行、打包升级、模型资源完整性、使用文档 | 完整安装包可在干净 Windows 环境运行，通过验收清单 |

依赖关系：
- P0 与 P1 可以交错推进，但 P0 失败时先解决基础能力再扩大美术投入。
- P2 可以先接测试模型，正式模型在 P3／P5 接入验收。
- P4 的接口梳理可以提前，专注状态迁移先于桌宠专注控制。
- P5 必须有真实模型和真实业务数据参与，不能只看孤立动画预览。

第一份可演示成果：一个真实透明桌宠窗口，使用测试或初版角色，敲左右键能驱动双手，音乐播放／暂停能切换状态，收到一次真实提醒能打开主应用。该成果只证明链路，不替代最终美术验收。

## 12. 建议代码与资源组织

以下为拟新增结构：

```text
pet/
  src/
    renderer/           # Cubism 适配、道具、资源加载
    behavior/           # 动作调度、状态与冷却
    keyboard/           # 键位布局、按键集合、手部映射
    bridge/             # Tauri 事件与业务协议
    components/         # 气泡、菜单、设置
  src-tauri/
    src/
      input/            # Windows Raw Input
      window/           # 命中测试、DPI、多屏
      bridge/           # 本机 HTTP/SSE、连接重试
  assets/
    characters/violet/
    props/
    audio/

violet_pet.py            # 桌宠进程管理、配对、配置
violet_pet_protocol.py   # 事件、状态、命令与校验
web/src/petBridge.js     # 主界面的音乐／编辑状态桥
docs/pet/                # 参数规范、协议、验收与交付说明
```

实际实现时按现有代码风格调整，不为目录结构强行拆分简单逻辑。业务变更仍在现有 service／desk 中提交；协议模块不另建一套任务或日记数据。

新增持久化内容应有限：
- 桌宠偏好：位置、缩放、模式、键盘／音效开关、快捷键、免打扰。
- 专注运行会话和去重 ID。
- 需要跨重启的提醒投递／稍后提醒记录。
- 协议版本、模型版本与资源校验信息。

业务数据库迁移纳入现有备份／恢复流程，先备份再迁移；保留原有任务、日记与播放记录。

## 14. 风险与应对

| 风险 | 影响 | 提前应对 |
|---|---|---|
| 原画漂亮但拆层不够 | 转头露洞、手无法自然敲键 | P1 用关键动作反推拆层，先验手臂和道具遮挡 |
| Live2D／WebView／透明窗组合问题 | 画面闪白、渲染异常 | P0 在目标机验证；必要时评估原生 Cubism 渲染外壳 |
| 原生点击穿透复杂 | 桌宠挡住其他软件或无法恢复交互 | P0 单独验证；保留托盘和快捷键恢复入口 |
| 主界面与桌宠各有一套状态 | 音乐、计时、任务不一致 | 明确播放器执行者与专注服务端权威状态 |
| 多路通知重复 | 同一提醒连续响多次 | 统一投递决策、ACK、事件去重 |
| 模型纹理和动画过重 | 常驻资源占用偏高 | 限制图集、按需资源、隐藏降频、在实测机调整 |
| 新技术增加发布复杂度 | 开发版正常而安装包失败 | P2 起就做打包冒烟，P6 用干净环境验证 |

若基础渲染路线需要调整，保留业务协议、角色资产和行为接口，避免把一次窗口技术问题变成整个项目重写。
